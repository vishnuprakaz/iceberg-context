## V4 upgrade strategy

Moving from v3 to v4 has to handle legacy manifests without a full metadata rewrite, which is prohibitively expensive for large tables. The consensus was an on-demand, incremental migration. V4 tables reference legacy v3 manifests and use metadata deletion vectors (MDVs) in the root manifest to track deleted files; when a file is modified its entry is promoted to v4 format, with v2 positional deletes converted to v4 deletion vectors. For column updates that add or re-instate a whole column, this is a full rewrite of the metadata into v4.

**Decisions:**
- V3 to v4 migration is gradual and on demand: v4 tables reference legacy v3 manifests, and entries are promoted to v4 format when modified.

## Reader and writer requirements and CDC

Writers must write new entries in v4 format, and legacy entries need full component conversion when promoted. Legacy readers must apply MDVs, and v4 readers use format-version routing. Change data capture remains functional by diffing file entries, identifying column updates through replaced/modified entry pairs, and snapshots keep supporting mixed operations (DV, update, insert).
