## Naming of index files

## Materializing expressions in index data files

The notes list cases: materialization is not needed when indexing a single identity column or a monotonic transform such as truncate, day or hour; it is needed for non-monotonic expressions like lower and for hash; and it could be useful with a locality preserving function like hilbert. The suggestion is to define index_values as a list of (field_id, expression) pairs. No agreement is recorded.

## Ranges stored in the index root manifest

The topic was storing tuple ranges for every leaf file in the index root manifest, enforcing that the same index_keys are in the same file. On what to store, the options were index_key results, which may duplicate values, or the index_key source; the suggestion is the results. On which bound, the options were min and max, min only, or max only; the suggestion is max only with a sorted index metadata file. On where, the options were a column stat for an index_key field id or a specific tracking file field; the suggestion is a new range_upper_bounds tracking file field. No agreement is recorded.

## Stats for leaf files

Stats would be stored in the index root manifest in content-stats for every leaf file, as column stats for every column used in the expressions and in the included-column-ids list. A possible problem noted is that there are no stats for metadata columns. On whether this should be prescribed or left to maintenance, the suggestion is to leave it to maintenance.

## Encryption and snapshot id uniqueness

Repeated from the previous agenda: if the tracking file is encrypted by key-metadata, store an encryption keys list and only the key-id, as in table manifest files, with the tracking file holding unencrypted key-metadata for the leaf files. A single index snapshot could point to any given table snapshot, and readers need to keep the tracking file location since it may change after index maintenance. The notes record no discussion or outcome.
