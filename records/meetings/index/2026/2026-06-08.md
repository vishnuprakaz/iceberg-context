## Summary

The index sync set out to close the remaining incremental-update items and decide whether an index is a table. The group agreed to reuse table implementation code and a near-identical spec while treating an index as not a table from the user and API view, with the spec forbidding overlapping files, column updates and partition specs. It agreed to reuse Iceberg's existing deletion vectors, to start with copy-on-write only and no update files, and to validate the spec with a hand-wired prototype and benchmarks first. Indexes are likely separate catalog objects linked by identifier, but that is not final. Permissions, REST and catalog RPC design, scale modeling and DDL semantics remain open.

## Index versus table

The agenda contrasted two views: an index is a different structure that shares manifest code and the Table API but not storage, or the index reuses the table model to get ACID, DVs, updates and pruning. The group agreed to reuse table implementation and library code and a near-identical spec, noting the commit path will be custom regardless so reuse is not the deciding factor. From a user and API view an index is not a table, and the spec forbids most table behaviors.

**Decisions:**
- Reuse table implementation/library code and a near-identical spec for indexes.
- An index is not a table from a user/API view: loading or writing an index as a table must fail.
- The index spec forbids overlapping files, column updates and a partition spec, and requires one mandatory transform sort order.

## Delete vectors and incremental updates

The agenda proposed a separate DV file in the existing format, an adds-only update file, and defaulting to leaf rewrite. The group agreed to reuse Iceberg's existing DV, since benchmarks showed no new delete format is worth introducing. It agreed to start with copy-on-write only and no update files, because for object-store-sized leaves a full leaf rewrite is about as cheap as maintaining an overlay update file plus DV; merge-on-read machinery would be added later only if benchmarks show it is needed, likely just for very large leaves. This differs from the agenda proposal, which kept an update file plus DV for large leaves with small change sets.

**Decisions:**
- Reuse Iceberg's existing deletion vector format for indexes.
- Start with copy-on-write only (no update files); add merge-on-read later only if benchmarks prove it is needed.

## Validate the spec with a prototype

The group agreed to validate the spec before formalizing it by building a quick hand-wired prototype, with Parquet files structured per the spec, and benchmarking it at real scales.

**Decisions:**
- Build a hand-wired prototype and benchmark it on real scales before formalizing the spec.

## Catalog representation and commit path

The group leans, without a final decision, toward indexes being separate catalog objects that the table links to by storing just an identifier, as with materialized views, and that do not appear in LIST TABLES. Indexes will need a commit path, but a simpler one than tables, with no stage-create.

**Open questions:**
- Are indexes separate catalog objects linked from the table by identifier (leaning yes, not final)?

## Open items

Four areas remain open: the permissions model, REST and catalog RPC design, scale modeling, and DDL-on-index semantics. On RPC design the notes say catalog RPC cost may dominate Parquet IO, so round trips should be minimized and index metadata ideally returned with LOAD TABLE.

**Open questions:**
- Permissions model: separate or inherited from the table?
- REST/catalog RPC design: how to minimize round trips, ideally returning index metadata with LOAD TABLE?
- Scale modeling: target rows per leaf versus leaf size versus metadata file count.
- DDL-on-index semantics: reuse table schema-update actions or define separate ones?

## Action items

- Look at what real databases do for index permissions.
- Build a quick hand-wired prototype (Parquet files structured per the spec) and benchmark it on real scales.
