## Summary

The Index Support Sync notes for 26 October 2026 cover open questions in the index draft spec and the index REST spec, as proposals without recorded agreement. For the draft spec, the suggestions are to store range file boundaries under a new name reusing the partition field id (102) and fields (1000 + i), to store the range file schema so the index works without source table information, and to allow stats-only fields. For REST, Huaxin's pull request was presented together with a single-file summary of the index-only changes, nine design decisions for community review, the endpoint list, and open questions on index name scope, discovery across namespaces and routes not yet included.

## Storing range file boundaries

The options were an extra field in the column stats, such as group_max_value as in the original version, or top-level fields in the tracking file for every range file. For the latter, either new field ids are reserved, which might clash with future manifest field ids, or the partition field id and the fields used for partition values are reused, since the logic is similar and they are not used in indexes. The suggestion is to use a new name and reuse the partition field id (102) and fields (1000 + i). No agreement is recorded.

References: [iceberg#16961](https://github.com/apache/iceberg/issues/16961)

## Range file schema

One option is to store identity, materialized and non-materialized fields and always generate the schema from the table snapshot schema. The other is to store an identity mapping from table column to range file column and use derived columns, which means derived columns are needed in V4, historical schemas must be tracked, and every source table column must be copied to the range files. The suggestion is to store the range file schema so the index can work without information on the source table. No agreement is recorded.

References: [iceberg#16961](https://github.com/apache/iceberg/issues/16961)

## Stats-only fields in indexes

The options were to disallow stats-only fields in indexes for a simpler spec, or to allow them as in the table spec proposal. The suggestion is to allow them, so that big computed fields such as Z-order values do not have to be stored. No agreement is recorded.

References: [iceberg#16961](https://github.com/apache/iceberg/issues/16961), [iceberg#18405](https://github.com/apache/iceberg/issues/18405)

## Index REST spec: design decisions and endpoints

Huaxin's REST spec pull request was listed, with the index-only changes collected in a single file for readability. Design decisions put to the community: all index routes sit under the namespace path without the table; index names are unique within a namespace; the indexed table is referenced by a full TableIdentifier and may be in another namespace, and the server never reads the table; listIndexes filters by table and index type but not snapshot; indexes are created without extracts and maintenance adds them with add-extract commits; rename uses a per-index route; only index-only operations are covered; commits carry a base-metadata-location and the server may reject or merge; updates reuse several table updates, add add-extract and remove-extracts, and require only assert-index-uuid. Index endpoints are not in the default endpoint set and must be advertised by servers.

References: [iceberg#16963](https://github.com/apache/iceberg/issues/16963)

## Index REST spec: open questions

Three groups of questions were listed. On name scope: whether names should be unique per table instead of per namespace, whether index names share the identifier space with tables and views, and whether the table filter of listIndexes should be required. On discovery: whether a catalog-level route should list a table's indexes across namespaces or indexes should be restricted or default to the table's namespace, and which permissions apply when they differ. Routes not yet included are unregister index, refreshing vended credentials, remote signing for index files, and ETag / If-None-Match on loadIndex.

**Open questions:**
- Should index names be unique per table instead of per namespace, and should they share the identifier space with tables and views?
- Should the table filter of listIndexes be required?
- Should a catalog-level route list the indexes of a table across namespaces, or should an index be restricted to, or default to, its table's namespace? Which permissions apply when they differ?
- Should unregister index, vended credential refresh, remote signing for index files, and ETag / If-None-Match on loadIndex be added?

References: [iceberg#16963](https://github.com/apache/iceberg/issues/16963)
