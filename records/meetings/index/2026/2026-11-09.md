## Summary

The index sync agreed to decouple derived columns from the index work: the derived columns proposal proceeds on its own track, derived columns come out of the index spec for now, and whether they land in table spec V4 or V5 is deferred. The proposal to nest index REST routes under the table, with index names unique per table and an optional namespace-level listing, was accepted. For the REST pull request, the group answered that indexes follow a table on rename and are dropped with it, and that multi-table indexes are out of scope. Whether loadTable returns indexes by default or behind a parameter stayed open, and index authorization is to be left to catalogs apart from a general read-restrictions statement. Reviewers asked to settle the index metadata spec before the REST spec.

## Derived columns in the index schema

Peter asked whether derived columns, needed to store values such as Hilbert curve values in index files, should exist only in the index schema or go into the table spec, and if so in V4 or V5; the notes record the table spec V4 as his preferred option. Ryan argued the index and table timelines must stay decoupled: design derived columns as a table feature through the existing proposal, but do not make the index work depend on a table format version. Dan added that derived values could also be materialized and that this case is far ahead of what indexes support today. The group agreed to continue both efforts in parallel and take derived columns out of the index spec until the proposal lands, at which point they come in through the shared schema.

**Decisions:**
- Derived columns are handled as a separate proposal; the index spec and table spec proceed independently of it.
- Derived columns are removed from the index spec for now and come back through the shared schema once the proposal is adopted.

## Index REST routes nested under the table

The host summarized research posted to the dev list: catalog and REST APIs scope indexes to the table, SQL databases are split between per-table and schema-level index names, most can list indexes across tables, and rename support varies. The proposal is to nest index routes under the table, make index names unique per table, and add an optional endpoint listing all indexes in a namespace; the notes record Dan's +1 on the dev list and Peter's preference for nesting. A participant worried about the mismatch with engine identifiers, since Spark has no fourth name level; the answer was that REST paths and SQL identifiers are not tied together and engines normally reach indexes through the loaded table.

**Decisions:**
- Index routes are nested under the table, index names are unique per table, and an optional endpoint lists the indexes of a namespace.

## Table rename, table drop and multi-table indexes

The open questions in the notes were answered in the meeting. Because indexes are sub-resources of the table, renaming a table moves everything under it, so its indexes follow. Dropping a table drops its indexes, since an index of a missing table can no longer be referenced; how the catalog does this, or whether it refuses the drop while indexes remain, is an implementation matter. Multi-table indexes were declared out of scope.

**Decisions:**
- Indexes move with their table when the table is renamed.
- Dropping a table drops its indexes; how is left to the catalog implementation.
- Multi-table indexes are out of scope.

> “once you drop the table the indexes are meaningless and they should probably be unreferenceable.” [0:23:24](https://www.youtube.com/watch?v=q-A9Y5FMRY8&t=1404s)

## Should loadTable return the table's indexes?

Ryan preferred that loadTable send back the index objects without a parameter, because a reader that finds an index will almost always load it and extra round trips should be avoided. Dan preferred not returning full index bodies by default, either returning only names, using the bulk load request, or having clients that understand indexes ask for them, because most loadTable calls never use the indexes and the extra work already loads catalogs, as with vended credentials. Ryan suggested distinguishing a load for the read path from a load for metadata instead of adding more parameters; Peter raised existing clients suddenly receiving indexes, which was answered as forward compatible because extra data can be ignored. Pagination of indexes in the response was judged unnecessary. No conclusion was reached.

**Open questions:**
- Should loadTable return indexes by default, only when requested through a parameter such as include-indexes, only as names, or through the bulk load endpoint?
- Should the REST API distinguish loading a table for reading from loading it for metadata only?

## Index access control and read restrictions

The notes propose that index access follows table access and that the server must not return an index when the caller has row filters or column masks on the table. In the meeting this was pushed back on: how authorization overlaps with indexes is up to catalog implementations and need not be defined in the spec. Ryan said read restrictions still need thought, for example when an index contains a masked column or lacks the column a row filter needs. The direction was a general statement in the read restrictions section of loadTable that restrictions apply whether the table, the index or both are read, so indexes must not expose data a restricted query could not return.
