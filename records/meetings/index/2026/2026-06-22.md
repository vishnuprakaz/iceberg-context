## Index is its own object, not a table

The group closed the question of whether an index is a table: it is its own object that reuses table machinery under the hood. The reasons given are that it requires a sort order, has no column updates, no partition spec and no overlapping ranges between leaves, inherits base-table permissions, and has its own CREATE, DROP and UPDATE INDEX DDL.

**Decisions:**
- An index is not a table; it is its own object that reuses table machinery under the hood.
- An index inherits base-table permissions and has its own CREATE/DROP/UPDATE INDEX DDL.

References: [iceberg#16961](https://github.com/apache/iceberg/issues/16961)

## Index as a separate catalog entity

The group decided that an index is a separate catalog entity with no pointers in table metadata. It has its own REST endpoints, and the catalog can optionally return index metadata with loadTable to avoid extra round trips. This keeps table and index updates independent and asynchronous.

**Decisions:**
- An index is a separate catalog entity with its own REST endpoints and no pointers in table metadata.
- The catalog can optionally return index metadata with loadTable.

References: [iceberg#16963](https://github.com/apache/iceberg/issues/16963)
