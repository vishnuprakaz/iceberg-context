## Summary

The V4 metadata sync notes for 13 July 2026 list three agenda items, mostly as open questions. The first was partial updates of content_stats for column files, including whether a nested struct field can be column-updated and whether a writer carrying stats over from the read can avoid a manifest scan. ## Partial update of content_stats for column files

The item covered how content_stats is partially updated when column files are written. Two questions were posed: whether a column update of a nested field in a struct can be supported, or whether content_stats should be flattened and the wrapper layer removed; and whether a writer that carries the data file column stats over from the read can avoid scanning the manifest file to fetch the stats in the manifest DV path. No answers are recorded.

**Open questions:**
- Can a column update target a nested field in a struct, or should content_stats be flattened and the wrapper layer removed?
- If the writer carries data file column stats over from the read, can the manifest scan in the manifest DV path be avoided?

## Utility of partition_spec_id with a union-schema tuple

The question was what partition_spec_id is for when the partition tuple is always the union schema of all specs at the time of the write. The notes say the spec projection is needed to tell tuples with explicit nulls apart from those without, which matters for equality delete matching (spec 1 with tuple A differs from spec 2 with tuple B containing nulls). They ask whether this need goes away when equality deletes go away.

**Open questions:**
- Does the need for partition_spec_id go away once equality deletes go away?

## Java API design for colocated DV and column files

The group looked at the Java API design document for colocated DVs and column files. The question recorded is one of consistency: if the DataFile interface exposes List<ColumnFile> columnFiles(), why not DeletionVector deletionVector() as well. No outcome is recorded.

**Open questions:**
- If DataFile exposes List<ColumnFile> columnFiles(), should it also expose DeletionVector deletionVector()?
