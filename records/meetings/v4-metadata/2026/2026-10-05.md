## Consolidating dv_snapshot_id and column_file_snapshot_id

Amogh Jahagirdar raised that the spec currently has separate dv_snapshot_id and column_file_snapshot_id fields, intended to allow a minimal projection during conflict validation or change detection. The benefit is unclear if a reader typically needs both sets of changes anyway, so the question is whether to consolidate them into a single modified_snapshot_id.

**Open questions:**
- Could dv_snapshot_id and column_file_snapshot_id be consolidated into a single modified_snapshot_id?

## Snapshot ID assignment for REPLACED entries

As currently proposed, change detection for REPLACED/MODIFIED pairs works off entries where dv_snapshot_id or column_file_snapshot_id equals the current snapshot ID. With a single modified_snapshot_id, the REPLACED entry's snapshot_id could be set to the previous modified snapshot ID (or the current snapshot ID if not previously modified). Changed entries could then be found where snapshot_id or modified_snapshot_id equals the current snapshot ID.

## Column files: dropping split_offsets and format_version

The proposed spec change drops split_offsets and format_version for column files. format_version would exist only for manifests and be stored in manifest_info.
