## Summary

The catalog sync spent most of its time on V3 table encryption with the REST catalog. The REST client cannot read encrypted tables today; a pull request adds a hybrid mode where the catalog vends storage credentials and KMS credentials come from client configuration, while a separate spec change has the server vend KMS credentials. Whether hybrid mode should sit behind a flag that is off by default was not settled, and the security model of routing KMS access through the catalog is to be checked with security people. Open-floor questions covered where read restrictions are enforced in engines, the state of V4 REST work, and the reason for a V2 load table endpoint, including that read restrictions stay optional for servers but clients that cannot honor them must fail. Three review requests were listed.

## V3 encryption with the REST catalog: hybrid mode and server-vended KMS credentials

Prashant explained that the REST client does not support V3 encryption at all today, so encrypted tables cannot be read through a REST catalog, and that the catalog currently vends only storage credentials. A pull request proposes a hybrid mode: storage credentials come from the catalog and the encryption manager uses client-side credentials to talk to the KMS; the longer-term spec work has the server vend short-lived KMS credentials as a KMS type plus provider properties (#17155, call for review). He argued hybrid mode should be opt-in behind a flag, because otherwise grants live in two places and the catalog cannot tell whether the client has KMS access. Another participant questioned the use case, since a cloud KMS can be covered by the policy in the vended storage credentials; the answer was a non-cloud KMS such as Vault with S3. Concerns raised were that funnelling key access and data access through the catalog may defeat the separation people want from a separate KMS, and that per-provider KMS configuration adds a matrix of properties to every FileIO. No default was agreed.

**Open questions:**
- Should hybrid mode (catalog-vended storage credentials, client-side KMS credentials) be behind a REST client flag that defaults to false?
- Is it acceptable from a security standpoint for the catalog to vend credentials for a separate KMS provider, or should a non-cloud KMS always be client-side configuration?
- Can KMS provider configuration be standardized so that each FileIO does not need provider-specific properties?

## Read restrictions: where the engine enforces row filters and column masks

A participant asked how masks returned by the server are protected when the engine runs client-side, where a user could capture the unmasked data. The answer was that proofs of concept exist for Trino, where the client-server split makes this unlikely, and for Spark through an extension, where injected code remains a risk, as it is for vended credentials. Work is under way in the Spark community, driven by Huaxin, to make this a native capability, and managed services push execution into a trusted constrained environment. The topic is not in the notes.

## V4 changes in the REST catalog and the V2 load table endpoint

Asked about V4 progress on the REST side, the answer was that Drew's pull request adds the new endpoint and already covers relative paths and the adaptive metadata tree; a branch will be created once more pieces land, and metadata updates wait for the check constraints, default values and stats-only fields specs to close. A V2 load table endpoint is needed because V4 tables cannot be served through the V1 endpoint without breaking existing clients, and it is a chance to drop some config-path properties. On read restrictions in V2, the clarification was that the field stays optional for servers; the requirement is on clients, which must fail if they receive read restrictions they cannot apply, something that could not be required on V1 without breaking older clients. Prashant said he will tighten the spec wording with a one-line change on the client expectation. The topic is not in the notes.
