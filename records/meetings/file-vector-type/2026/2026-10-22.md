## Type serialization: float[256] vs vector(float, 256)

The question was how the type should be serialized. The notes state a preference for vector(float, 256) to avoid potential confusion, at the cost of a slightly more verbose type definition, and highlight vector(float, 256) as the result.

**Decisions:**

## Default values for vector columns

The proposal was to restrict both initial-default and write-default to null, because use cases may be lacking and a default vector value is expensive to write in JSON; the implication is that a required vector column can no longer be added later. Discussion notes mention a function to provide a zero or normalized vector as default, and a view that being unable to add a required vector field might not be a reasonable restriction despite the limited use case. The last note on the item is to only allow null and accept the restriction. Separately, check constraints might need to revisit how they handle defaults when a default value violates the constraint.

**Decisions:**
- Only allow null for the initial-default and write-default of vector columns, accepting that a required vector column cannot be added later.

## Is vector a primitive type?

The question, tied to a review comment on a pull request, was whether vector is a primitive type or whether the spec should define primitive types in a way that excludes it. Points noted: vector is structurally similar to but semantically different from list, the current spec has primitive, semi-structured and nested types, a primitive is usually a scalar value, and the choice may affect visitor code and whether a field id is assigned to the element. Options mentioned were a separate complex type, or splitting primitive into scalar and complex and recategorizing geo. The definition was deferred, since the implementation could help uncover the answer.

**Decisions:**
- Defer the decision on how to categorize the vector type; implementation experience should inform it later.

**Open questions:**
- Is vector a primitive type, a separate complex type, or something else?

## Lower bit width element types (int8, uint8, float16)

The group discussed whether to introduce lower bit width types. Notes include that it may be too early or a v5 matter, that allowing vectors to hold types outside the current type system is too complex, a preference for an incremental approach, and caution about rushing to a solution. Other points were the dependency on GPU vendors for types such as half float, keeping the Iceberg surface clean while engines handle the Parquet-specific representation, and how Java handles half float for Parquet without native support. The next step is to focus on float16, tracing the path through Parquet and different programming languages and asking what is gained; Peter is to take a look.

**Open questions:**
- What is gained by encoding float16, given that current engines might not support float16 in memory?
- How does Java handle half float for Parquet without native half float support?
