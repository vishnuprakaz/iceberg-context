## float16 test results and narrow element types

Peter presented float16 test results from the mailing list discussion, and the notes mention direct access to vector bytes and the choice between an element type and a generalized encoding. A middle ground was raised: spec guidance letting engines, writers and readers treat float32 as float16 in the physical representation, separating that from what is captured at table level. Concerns were that waiting until a file is opened to know the exact type might be too late, and whether the exact width is needed at planning time or is an engine detail. Options listed were adding well-defined types largely for vectors, non-standard annotations that are not interoperable, or vector-only support that could be overly specialized; v5 and catalog labels for extra optimization information were also mentioned. A project priority order of spec, interoperability, performance, flexibility was noted, and no decision is recorded.

**Open questions:**
- Should narrow element types such as int8 and float16 be added to the type system, expressed as annotations, supported only for vectors, or left to the physical representation?
- Is the exact element width needed at planning time, or is it an engine implementation detail?
- At which level should this be supported: not at all, at the Parquet level, or at the Iceberg schema level?
