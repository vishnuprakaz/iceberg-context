## Design discussions

- **Secondary indexes** (Index Support Sync): the group agreed to nest index REST routes under the table with index names unique per table, to move and drop indexes with their table, to leave multi-table indexes out of scope, and to remove derived columns from the index spec until the separate derived-columns proposal lands. Whether `loadTable` returns indexes by default stayed open, and reviewers asked to settle the index metadata spec ([#16961](https://github.com/apache/iceberg/pull/16961), open) before the REST spec ([#16963](https://github.com/apache/iceberg/pull/16963), open). [Record: index sync 2026-11-09](../../records/meetings/index/2026/2026-11-09.md); [summary on the dev list](https://lists.apache.org/thread/mqpz7pfhztx79r5ok0m7j4r7l3yovktq).
- **Materialized views** (Materialized View Sync): the spec draft [#11041](https://github.com/apache/iceberg/pull/11041) was opened for broader review on 2026-11-10, with proof-of-concept implementations in Spark and Trino ([thread](https://lists.apache.org/thread/zpl1pk6v7k49s30gmm3kr986bc9y7jyv)). The sync decided to stop preparing and call the vote; the notes describe the spec as independent of the table spec and V4, and a REST spec for materialized views is still to be defined. [Record: materialized views sync 2026-11-12](../../records/meetings/materialized-views/2026/2026-11-12.md) (the notes include AI-generated text).
- **REST catalog changes for V4** (Catalog Community Sync): the thread converged on changing the REST models in place plus a v2 `loadTable` endpoint that V4 tables must be loaded through. On 2026-11-11 a `rest-v4-changes` branch was created for the spec changes, and feedback is asked for on [#17642](https://github.com/apache/iceberg/pull/17642) (open). [Record: thread](../../records/threads/2026/08/discuss-initial-irc-changes-needed-for-iceberg-v4-4fdcd7.md); group page: [Catalog](../../groups/catalog.md).
- **Name mapping for files that carry only some field IDs** (dev list, no working group; found through the [shared conformance testing](../../initiatives/conformance-testing.md) work): Java, PyIceberg, iceberg-rust and iceberg-go resolve such Parquet files differently. The proposal is per-field resolution; the latest message argues that per-file fallback was the original intent and that partial-ID support should restart as a new feature discussion, so there is no agreement. [Record: thread](../../records/threads/2026/11/discuss-name-mapping-for-data-files-that-carry-only-some-field-ids-14cfe6.md).
- **Orphan file listing with catalog credentials** (Spark Community Sync): after ten messages this week, [#17862](https://github.com/apache/iceberg/pull/17862) (open) was reworked to take the Hadoop configuration from the table's FileIO when it is `HadoopConfigurable`, with no new API. The S3FileIO case is left to a future parallel listing through FileIO, whose design is still being discussed. [Record: thread](../../records/threads/2026/10/discuss-spark-use-the-catalog-s-hadoop-configuration-when-listing-orph-4ba0b5.md); the pull request is also on the review list of the [Spark sync 2026-11-11](../../records/meetings/spark/2026/2026-11-11.md).
- **Batch remote signing for the FILE type** (dev list; related group: [File and Vector Type](../../groups/file-vector-type.md)): reviewers want the request shape to follow from how a catalog authorizes FILE references, with an optional spec-defined context (data file location and field ID). The proposer agreed on the semantics and argued the context can be added later; [#18254](https://github.com/apache/iceberg/pull/18254) is open and the thread stays open while the FILE implementation settles. [Record: thread](../../records/threads/2026/10/discuss-rest-spec-batch-remote-signing-endpoint-019f2b.md).
