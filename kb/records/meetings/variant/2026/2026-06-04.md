## Summary

The Variant sync on 4 June 2026 centred on shredded read performance. Benchmarks on 10M and 100M rows show shredded variant reads about 4 to 5 times slower than unshredded, because vectorization is disabled for shredded variants and there is no sub-field projection, so the whole variant is reconstructed. ## Benchmarks: shredded variant reads are slower

Benchmarks re-run on main, which now includes shredded write (#14297), with 10M rows, default auto-inference and a 100-row buffer show shredded reads 4.0x to 5.0x slower than unshredded variant across flat projection, nested projection, filter and aggregation; the picture is the same at 100M rows (4.1x to 5.4x). The notes give two structural causes, both described as fixable: vectorization is explicitly disabled for shredded variants, forcing row-at-a-time reads, and there is no sub-field projection, so all shredded typed_value columns are read whatever the query needs. On the write side the cost is parse_json plus per-shredded-field Parquet column encoding, so the lever is how many fields are selected for shredding.

References: [iceberg#14297](https://github.com/apache/iceberg/issues/14297), [iceberg#16292](https://github.com/apache/iceberg/issues/16292), [iceberg#16448](https://github.com/apache/iceberg/issues/16448), [video](https://www.youtube.com/watch?v=HW80v23j7Jw)

## Read path: sub-field projection

Qiegang is developing sub-field projection so that queries no longer reconstruct the entire variant. Iceberg handles project and filter queries; Spark needs a new rule to extract sub-fields from aggregate and join expressions so they become eligible for pushdown. The notes call this work critical to making shredded variants performant. Ryan Blue will review the upcoming PRs.

References: [iceberg#16448](https://github.com/apache/iceberg/issues/16448)

## Automated inference over a user-declared shredding schema

A proposal for a user-declared shredding schema, from the document on variant shredding policy across Iceberg implementations, was debated. The community was not in favor: it makes users manage complex configurations that go stale, and it cannot adapt to data patterns such as shredding different fields per file based on data clustering. The new direction is to improve automated inference. The community will define a canonical inference algorithm for consistent shredding across implementations, considering statistical sampling (for example jackknifing) to estimate field entropy from a small sample, shredding a field only when its type is uniform across records, and testing strategies on real-world data.

**Decisions:**
- The community was not in favor of a user-declared shredding schema; the focus moves to improving automated inference algorithms.
- The community will define a canonical inference algorithm for shredding across implementations.
