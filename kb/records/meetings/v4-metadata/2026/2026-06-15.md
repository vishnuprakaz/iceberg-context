## Implementation milestone 1

Steven W presented milestone 1 of the v4 implementation. It keeps the metadata tree at a fixed two-level shape, root manifest to leaf data/delete manifests, and uses copy-on-write leaf rewrites for all mutations. Direct data-file content entries in the root manifest (a small-write optimization), manifest delete vectors at the root level, and column-file DV updates are reserved for follow-ups. The goal is end-to-end parity with v3 commit and scan paths so v4 tables can be read and written through the existing API; later optimizations are independent of each other and can be built in parallel.

## DV snapshot ID on leaf manifests

Amogh J noted that the current implementation sets the DV snapshot ID whenever replaced positions or deleted positions are set, and argued it should not. His reasoning is that the DV snapshot ID only applies to change detection for leaf data files, and the diff DV (replaced positions plus deleted positions) already implies the changes for that leaf manifest. He also raised inheritance of the DV snapshot ID and column file snapshot ID. No outcome is recorded.

**Open questions:**
- Should the DV snapshot ID be set on leaf manifest entries when replaced or deleted positions are set?
- How should DV snapshot ID and column file snapshot ID inheritance work?

## List<ColumnFile> vs base file plus overlay list

Amogh J recalled that the previous discussion leaned towards a List<ColumnFile>, where the original base file must be the first element of the list and must have no fields set. He wanted to confirm that this is the general consensus, since the spec pull request would need to be updated. The notes do not record the answer.

**Open questions:**
- Is List<ColumnFile>, with the base file as the first element and no fields set, the agreed representation?
