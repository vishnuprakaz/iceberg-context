## Summary

The Index Support Sync of 17 August 2026 went through open questions in the index draft spec. The group agreed to define index_keys as a list of Iceberg expressions that determine how the index is ordered, and not to restrict which functions those expressions may use: engines that do not understand an expression can skip the index. It also agreed that index region (leaf) files are sorted by the index_keys values. Using included_column_ids to define the content and schema of the region files was generally seen as a good approach. A discussion started on whether the index_key expression results should also be stored in the region files. Agenda items on stats, encryption and snapshot id uniqueness have no recorded outcome.

## Index keys as Iceberg expressions

The agenda proposed index-keys as an array of Iceberg expressions, limited to iceberg_functions or sql_functions with no engine-specific functions or UDFs, and only expressions returning primitives. The group agreed to use a list of Iceberg expressions to define index_keys, which determine the index ordering. It agreed not to restrict the functions usable in those expressions, which differs from the agenda proposal; engines that do not understand an expression can choose not to use the index.

**Decisions:**
- Use a list of Iceberg expressions to define the index_keys, which determine how the index is ordered.
- Do not restrict the functions that can be used in index_keys expressions; engines that do not understand an expression can choose not to use the index.

## Ordering of index files

The agenda proposed a global ordering based on the index-key expression results, with entries of equal keys ordered by source_file_path ascending and then by source_file_pos, applied to both the tracking file and the leaf files. The group agreed that index region files (leaf files) should be sorted by the values generated by the index_keys.

**Decisions:**
- Index region files (leaf files) are sorted by the values generated by the index_keys.

## Included column ids and region file schema

The proposal was that included-column-ids is an array of schema field ids, with no transform in the leaf file content. The resulting schema keeps each included column's name, type and value from the original table and adds source_file_path (field id 2147483538) and source_file_pos (2147483537). The group generally felt that using included_column_ids to define the contents and schema of the region files could be a good approach.

## Storing index key results in region files

The group started discussing whether the results of the index_key expressions should be stored in the region files alongside the included columns. In some cases storing them could help readers optimize lookups within a region file. In others the values can be derived when needed, so storing them would be redundant and could hurt performance by making region files larger. The question was left open.

**Open questions:**
- Should the results of the index_key expressions be stored in the index region files alongside the included columns?

## Agenda items without recorded outcome: stats, encryption, snapshot id uniqueness

The agenda proposed storing stats in the tracking file's content-stats for every leaf file: only the max index-key expression result, needing a new reserved range of stat column ids, plus column stats for columns used in expressions and included columns. For encryption it proposed an encryption keys list with only the key-id stored when the tracking file is encrypted, and unencrypted key-metadata for leaf files in the tracking file. It also noted that a single index snapshot could point to any given table snapshot and that readers need to keep the tracking file location. The meeting summary records no outcome on these.
