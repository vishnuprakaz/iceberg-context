## Removing the _pos field from column files

Anoop asked whether the _pos field is still needed now that column files are positionally aligned. The meeting concluded on removing it: writers are free to add it, but it will not be in the spec or in the Java implementation. The AI-generated notes give as rationale that this avoids ambiguity over the source of truth and prevents field ID conflicts between a data column and a metadata column, and that implementations can still generate position as a metadata column internally.

**Decisions:**
- Remove the _pos field from the column file in the V4 spec; writers may add it, but it is not specified and not part of the Java implementation.

## Sequence numbers and equality deletes with column updates

Anoop raised how the sequence number changes with column updates. According to the AI-generated notes, column updates will use the base file's data_sequence_number to track the latest row modifications, as an extension of its role as the inherited sequence number. Equality deletes are not supported for column files: existing equality deletes on a file must be converted to deletion vectors before a column update is applied, so that a file cannot end up with some rows affected by an equality delete and others not.

## Column file read path: API exposure and placement relative to FormatModelRegistry

The AI-generated notes record two decisions on the read path. Column files are exposed through the DataFile interface rather than ContentFile, because ContentFile is an internal abstraction and DataFile represents a complete data file (base plus columns). The read path is built above the FormatModelRegistry, which keeps the registry for reading single physical files, puts the multi-file stitching logic in a new reusable layer, and avoids multi-file inputs and engine-specific stitching in the registry API.

**Decisions:**
- Expose column files via the DataFile interface, not ContentFile (AI-generated notes).
- Build the column file read path above the FormatModelRegistry (AI-generated notes).

## Row alignment and vectorized reads

The problem was that file formats such as Parquet and Avro have different physical layouts and batching behaviour, so byte-offset seeking cannot be relied on to align readers. The solution in the AI-generated notes is row-offset based seeking: a primary reader, for example for the base file, uses the byte-offset split from the scan task and determines its starting row position, and the column file readers seek to the same row position with format-specific methods. For vectorized reads the stitching layer aligns batches of varying sizes by row position and combines them; over-reads from column files beyond the primary batch's row count are ignored.
