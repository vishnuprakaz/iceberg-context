## Column file representation

The dev list proposal left the representation to the implementation, and the meeting pushed back on that: it would force every implementation to support the superset, including files with only the live rows rather than rows with filler values. The argument made was to mandate rows with filler values in the spec. The group decided on a dense format, which simplifies readers by allowing direct batch reads without row alignment logic. Fillers are null, with required columns made optional in the file schema, so that min/max bounds are not polluted and existing Parquet/Arrow null handling is used.

**Decisions:**
- Column update files must use a dense format with filler values for deleted rows.
- Required columns are made optional in the column file schema and filler values are written as null, to preserve stats.
- Writers should write null for rows known to be deleted at write time; this is a 'should' requirement so that a DV applied mid-write does not invalidate files.

## Updates on partition tuples

The notes state that the partition tuple in file metadata must always match the file's content. Updates are allowed, including moving a file to an unpartitioned state by unsetting its tuple.
