## V4 writers: stats schema handling

When a manifest is rewritten, the stats read schema is built from the full table schema (for example 5,000 fields) while the writer may have produced stats for only a subset (for example 100), which makes reads inefficient and risks data loss. The solution is to build the stats read schema from the table's current metrics config in table properties, so only relevant stats are read and stale stats from earlier configs are not carried forward. This differs from v3, which copied the stats blob blindly, and it allows manifests to be cleaned of stats for fields no longer tracked. Concurrent writers refresh table state before commit, and the risk of a writer losing new stats from a concurrent commit was considered low and acceptable.

**Decisions:**
- The stats read schema for manifest rewrites is constructed from the table's current metrics config (table properties).
- The risk of a writer losing new stats from a concurrent commit is considered low and acceptable.

## V4 writers: commit operation intent

The operation field in snapshot metadata is ambiguous: it can mean the user's logical intent (for example MERGE INTO) or the physical changes (for example only appends occurred). The decision was that it represents logical intent, because conflict detection and validation depend on it: an OVERWRITE needs different validation from an APPEND even if it only adds files. The recent change that converts an OVERWRITE to an APPEND when no files are deleted is to be reverted. On the API side, v4 will likely consolidate operations into a more general UpdateFiles interface, and MergingSnapshotProducer will be refactored to separate v3 and v4 logic, possibly through a new base class or internal utility.

**Decisions:**
- Snapshot operations represent logical intent, not the physical file changes.
- Revert the recent change that automatically converts an OVERWRITE to an APPEND when no files are deleted.

## V4 manifest format: Parquet-only

The question was whether v4 manifests should support both Parquet and Avro or only Parquet. The decision was Parquet-only. The reasons given were performance (Parquet allows column projection for stats, which Avro does not), simplicity (one format is easier for integrations to implement), and consistency with the project's focus on read performance. The proposal will be posted to the dev list for final community feedback before it is added to the spec PR.

**Decisions:**
- V4 manifests will be Parquet-only, subject to final community feedback on the dev list before it is added to the spec PR.
